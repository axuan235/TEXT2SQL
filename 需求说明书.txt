### 什么是特征？
  特征是描述实体在某个维度的具体取值，比如性别男。特征计算时自定义的一种中间过渡计算逻辑描述语言特征计算（DSL），旨在方便的描述实体每个维度的SQL的计算逻辑，包含且仅包含该字段的计算逻辑。旨在无论该字段再何种情况下与哪些其它信息共同计算时，最终提取的特征DSL是一致的。
  特征组表示一个特征的计算路径和特征的自然语言描述，以下为一个示例
  案例1： 学生的平均分
  ··· DSL
  student.avg_score -> t_student.reduce('student_id', 'avg(score) as avg_score').avg_score  
  ···
  案例2： 学生的性别
  ··· DSL
  student.gender -> t_student.gender  
  ···  
  其中`t_student`是指表

### 特征的描述
   特征的标准描述 ==>>  业务_主体_限定词组_(维度)属性 ： 值域（取值范围）. 完整的清晰的特征描述 包含 维度描述和值域描述，维度分 业务空间[D]、主体[S]、限定词组[C]、(维度)属性[O]四部分组成， 比如 链家访客_用户_最近三天_访问次数： >5 。其中限定词可能缺省或者多个，业务在口语描述中一般缺省。 

### DSL基础语法
   有7个基础语法， map、reduce、filter、union、join、limit、sort
   1. union 的用法： .uion([table]) 仅仅支持两表合并，字段必须能对应，不能则需要现对字段进行合理筛选。多表union时需要写成 t1.union(t2).union(t3)
   2. join 的用法： .join([table],[join_type],[join_condition]),参数包含三个部分 关联的表、关联类型、和关联条件。注意：一次只能关联一张表，关联类型与sparkSQL支持一致，关联条件 必须是同时包含两表的字段的条件或者1=1这种全关联，仅包含单表的条件由filter处理。
   3. reduce的用法：.reduce([key], [cal_info]),reduce与spark的reduce类似，即表示接下来的计算需要shuffle过程，也与SQL种的group对应。key就是shuffle的key，cal_info与sparkSQL的聚合函数保持一致。
   4. map的用法： map([cal_info]), map 表示一行输入对应一行输出的计算，与不包含 join、group的SQL种的select计算列信息对应。 注意为了保证语法的一致性，SQL中 ```row_number() over (partition by ...)```这类分窗函数内部虽有shuffle逻辑也采用map表达，但在计算规划时可能需要区分考虑。
   5. filter的用法： .filter([condition]) 这里的条件与sparkSQL一致。
   注意： 1. 不支持spark的flatmap操作，特征计算往往是多行变一行，几乎没有一对多场景。 2. sort、limit操作一般出现在最后取数阶段，与维度计算无关，这里不定义使用方式，开发者自行完善。  
   
   示例：
  ··· DSL
  student.avg_score -> t_student.filter('grade=\'2\' and  class=\'3\'').map('score-60 as score ').reduce('student_id', 'avg(score) as avg_score').avg_score   
  ···
  如上DSL表示从t_student表中选出2年级2班的信息后，分数减去60分作为最终分数。并且按照学生编号计算平均分。另外特征计算中并不会记录中间过程选择哪些字段保留，只会记录对原表字段进行过哪些处理。 最终计算规划时根据实际字段依赖进行选用。
  
  
### 为什么从特征描述和构建SQL模型    
  人类思维中往往是从结果构建实现路径，比如广告投放，比如房地产广告投给哪些人呢？首先要有需求，可能是生娃了需要换大房子，也能能是结婚需要买房或者纯粹投资，然后是有购房能力，可能从职业或者理财产品或者收入等侧面进行筛选，最后还有其他约束，比如地域，预算，户型偏好。然后我们会分别考虑每一个维度如何进行评估（计算）。考虑清楚后SQL工程师会考虑怎么SQL实现，这时候才考虑计算规划的问题，比如哪些特征可以一起进行计算。从特征描述/构建模型天然就是符合人的思维习惯。而正常的一个SQL往往同时计算多个维度的信息的一部分计算过程，这给后续知识参考带来巨大麻烦。从特征描述既符合人类思维也方便后续知识检索。

## 特征抽取
   特征抽取由两个使用场景   
   场景1： 我们企业由大量的历史激烈模型SQL日志，是现场分析师根据客户需求实现的模型SQL，但是由于分析师偏好和功底不同，可能SQL虽然实现了逻辑但是计算并不是最优，另外计算结果字段命名可能存在差异性，需要进行规范统一。最终确保知识库对同一个业务属性只会保留一条DSL计算路径。
   场景2： 我们的知识库可能无法检索出某个维度属性的计算DSL，这个时候直接将该维度描述清楚由大模型生成后，录入 特征结构-DSL库。这种情况下可以要求大模型不要使用某些非常规用法或者其他语法建议。
   
   ### 功能目标
   从一组SQL模型中提取每一个字段的计算逻辑（DSL语言），然后进行计算逻辑优化后。 将限定词 与 特征结构的部分拆开，分别存入限定词知识库和主体属性知识库（入库前需要去重校验）。
   ### 计算优化
       一个DSL计算路径在保证计算结果不变时，一般先filter/map/union/reduce/join 是最优的计算顺序。请在最后的项目说明文档中补全任意两个操作交换时是否影响计算结果。
   
### 特征结构库
	  示例：
	  ··· DSL
	  student.bar_score -> t_student.filter('grade=\'2\' and  class=\'3\'').map('concat(first_name,last_name) as full_name').reduce('student_id', 'avg(score) as bar_score').bar_score   
	  ···
	  如上DSL表示从t_student表中选出2年级2班的信息后，将姓和名合成全名。并且按照学生编号计算平均分。
	  这个计算路径：
	  1. 限定词部分 .filter('grade=\'2\' and  class=\'3\'') 与特征集构无关需要移除。
	  2. 字段生成部分 .map('concat(first_name,last_name) as full_name') 该部分与计算的语义无关，移除后计算结果并不改变，移除。
	  3. bar_score命名不规范, 建议使用 函数_参数字段 进行命名为 avg_score.
	  最后收录的的特诊结构就是：
	  student.avg_score -> t_student_score.reduce('student_id', 'avg(score) as avg_score').avg_score  ==>> [教务系统] 学生 平均分
	  详细json格式如下：
	  ``` json
	   {
	      "feature_struct": "t_student_score.reduce('student_id', 'avg(score) as avg_score').avg_score",
		  "name": "avg_score",
		  "rule_trans": "从t_student表中按照学生编号分组，对分数取平均值" 
		  "valid_tans" : "教务系统[D]学生[S]平均分[O]", 
		  "table_list": ["t_student_score", ""]
		  "MD5":"....."   # 结构体的唯一ID，用于去重
	   }
	  ```
	  最后的项目说明文档中需要补全字段的命名规范。 valid_tans这个属性属于人工标注内容，首次写入知识文件时留白即可。知识库用纯文本管理即可，方便人工核验后生效。

      .filter('grade=\'2\' and  class=\'3\'')


## 特征生成
	生成过程分为三步：
	1. 结构化特征描述： 将特征的 业务空间[D]、主体[S]、限定词组[C]、(维度)属性[O]进行切分，分为 主体_属性 和 限定词列表两个部分。
	2. 知识库检索元素： 建议使用embeding模型接口，分别检索出  主体_属性、 各个限定词列表的命中内容和相似度。如果任意内容相似度过低,调用大模型生成SQL后通过特征提取获取改特征的计算DSL。
	3. 限定词参数示例化： 限定词结构中的参数实例化，因为compare_struct的参数被mask了，需要从语义中提取出取值，然后结合表字段信息中的翻译配置信息反向进行字典映射或者其他操作，得到正确的条件。
	4. 生成候选集与候选集筛选： 通过检索到的 特征结构和条件结果进行全量组合，需要注意特征结构与过滤条件之间存在的表一致性约束，另外需要同时基于特征结构的语义和条件的语义生成特征候选集对应的结构化语义。
	5. 特征计算筛选： 建议使用参数量小的大模型或者或者bert模型、embeding模型从候选集中选出语义最佳的结果，如果相似度过低，采用大模型生成SQL后通过特征提取获取改特征的计算DSL。
    6. 保留基于特征的取数逻辑： 如下为示例
	    student.filter("avg_score>60 and birth_year>1999 and gender=1").limit(10)[full_name, avg_score,test_type,count_1]
		上述语法表示对学生中符合"avg_score>60 and birth_year>1999 and gender=1"选择10条记录，仅保留 full_name, avg_score,test_type,count_1字段。

### 计算规划 
	
	计算规划首要任务是需要检测各个特征的共同计算是否包含共同计算的基础，如果包含他们则可以写在同一个SQL中。
	1. 首先你需要整理一份明细表，记录各种情况下计算路径是否具备公共基础以及计算如何合并。
	2. 然后实现你的逻辑，注意当存在多种可能性时选择最优的组合性。
	3. 分析计算需要的字段依赖，将计算结构树转成SQL模型
	
	以下为一个计算合并的例子：
	```
	#学生期末考试的平均分
	student.avg_score -> t_student_score.filter('test_type=\'期末\'').reduce('student_id', 'avg(score) as avg_score').avg_score
	# 学生的性别 (原始表字段)
	gender -> t_student.gender
	# 学生期末考试的考试次数
	student.count_1 -> t_student_score.filter('test_type=\'期末\'').reduce('student_id', 'count(1) as count_1').count_1
	# 测试类型 （原始表字段）
	student_id -> t_student_score.student_id
	student_id -> t_student.student_id
	```
	其中学生的性别和学生的平均分、考试次数出发的数据源不同，不具备共同计算前提。
	而 学生期末考试的考试次数和学生期末考试的平均分.首先表相同，filter的条件（可合并），然后shuffle的键相同，计算信息可以单纯拼接，同时计算两个字段。
	然后 student_id 作为原始字段 过滤和基于student_id的聚合，并不会导致字段含义变化和字段丢失，也可以一并取出。
	注意： 
	    1. 按照A字段聚合与按照A,B字段聚合是可以转化成由共同计算的，按照A字段聚合可以改为按照A，B字段聚合后，再基于聚合结果按照A字段聚合。实现中可以考虑该计算规划逻辑。
		2. 如果计算特征包含不同的表，则需要检索各个表的字段含义，找出关联字段，并自动补充道待规划的计算路径中。同时需要支持从配置文件中配置表的关联键

    规划好计算结构树后需要将其合理切分生成SQL。具体逻辑需要考虑两点：
	1. SQL的执行循序然后结合计算规划的算子顺序进行匹配后对树合理分割。	
	2. 需要支持取数逻辑表达式的转写
